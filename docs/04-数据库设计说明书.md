# 04 数据库设计说明书

## 1. 设计目标

- 严格保留原文七张业务表的字段口径。
- 增加主键、外键、唯一约束、CHECK 和索引，保证可校验、可查询。
- 业务库与 ADS 结果库同属 chronic_disease，便于后端只连一个库。
- 所有建表脚本可重复执行，不破坏其他数据库。

## 2. 业务表清单

| 表 | 说明 | 主键 | 外键 | 实测行数 |
|---|---|---|---:|---:|
| patient_info | 患者基础信息 | patient_id | - | 100,000 |
| disease_record | 慢性病记录 | record_id | patient_id | 165,087 |
| health_checkup | 体检指标 | checkup_id | patient_id | 300,022 |
| lifestyle | 生活习惯 | lifestyle_id | patient_id（唯一） | 100,000 |
| visit_record | 就诊记录 | visit_id | patient_id | 550,070 |
| medication_record | 用药记录 | med_id | patient_id | 549,587 |
| follow_up | 随访记录 | follow_id | patient_id | 300,390 |
| **合计** |  |  |  | **2,065,156** |

## 3. 关系设计

- patient_info 是主表，其余 6 表通过 patient_id 关联。
- disease_record、health_checkup、visit_record、medication_record、follow_up 为 1:N。
- lifestyle 通过 UNIQUE(patient_id) 保证 1:1。
- 外键统一 ON UPDATE CASCADE ON DELETE RESTRICT，避免误删患者造成孤立记录。
- 没有建立医生表、医院表、药品字典表：原文未提供，doctor_id/hospital/drug_name 为文本或编号；不擅自扩展业务口径。

## 4. 约束设计

| 表 | 约束 |
|---|---|
| patient_info | gender 男/女；age 0-120；id_number/phone 唯一；patient_id 主键 |
| disease_record | severity 轻度/中度/重度；diagnose_date 非空；外键 |
| health_checkup | sbp 60-300；dbp 30-200；血糖 1-40；BMI 12-50；心率 30-220；sbp>dbp |
| lifestyle | 吸烟/饮酒/运动/饮食枚举；睡眠 0-24；吸烟量 0-100；patient_id 唯一 |
| visit_record | 类型 门诊/急诊/住院；金额非负；cost=insurance_pay+self_pay；住院 0-365 天 |
| medication_record | end_date>=start_date；费用非负；is_effective 是/否 |
| follow_up | 随访方式/症状/依从性枚举；next_follow_date>=follow_date |

## 5. 索引设计

- 所有 patient_id 外键建立普通索引，支撑患者详情与关联查询。
- disease_record(disease_type, diagnose_date)：疾病分布、趋势。
- health_checkup(checkup_date)：最近体检、评分。
- visit_record(visit_date)、visit_record(visit_type)、visit_record(department)：就诊分析。
- medication_record(drug_name)、drug_type、start_date：用药 TOP/类别/趋势。
- follow_up(follow_date)：随访查询。
- patient_info(province, city)、create_time：画像与筛选。

## 6. ADS 表设计

ADS 共 15 张：

1. ads_overview：大屏总览（1 行）。
2. ads_patient_profile：性别/年龄/省份/交叉（33 行）。
3. ads_disease_dist：疾病类型（10 行）。
4. ads_severity：疾病×严重度（30 行）。
5. ads_comorbidity：共病数量（3 行）。
6. ads_risk_factor：因素×疾病/指标（70 行）。
7. ads_visit_analysis：类型/科室/年度（18 行）。
8. ads_medication_analysis：TOP/类别/有效率/联合（108 行）。
9. ads_drug_by_disease：疾病 TOP3（30 行）。
10. ads_trend：年度/月度/年度疾病/预测（188 行）。
11. ads_health_score：逐患者评分（100,000 行）。
12. ads_health_level：五级分布（5 行）。
13. ads_data_quality：七表质量（7 行）。
14. ads_module_run：模块运行记录（8 行）。
15. ads_module_kpi：模块 KPI（7 行）。

## 7. 为什么把结果写入 MySQL

- 原文结果在 HDFS；本项目已将 12 张 ADS 写 HDFS，同时写 MySQL ADS 保证后端稳定读取。
- 结果表与业务表同库，便于事务外只读查询、分页、筛选。
- 仍保留 HDFS/Hive DDL 与同步脚本，部署到 Linux 集群时可切换。

## 8. 建表与检查脚本

- sql/mysql/01_schema.sql：7 张业务表。
- sql/mysql/02_ads_schema.sql：15 张 ADS 表。
- python/chronic_disease/load_mysql.py：建表 + 批量导入 + 行数核对。
- python/chronic_disease/quality_check.py：30+ 质量检查。
- scripts/generate_data_dictionary.py：从 information_schema 生成字段字典。

## 9. 数据量口径

10 万 = patient_info 的患者人数，不是七表行数之和。七表总行数 2,065,156 单独统计，并在 ads_overview 与质量报告中分别展示。

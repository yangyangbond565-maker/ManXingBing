# 常见答辩问题与参考答案

## 1. 为什么选 MySQL + Spark + Hive + HDFS？

MySQL 适合业务事务和七表关系；Hive/HDFS 适合离线数仓和原始数据存储；Spark 做批量分析；Spring Boot 提供稳定 API；Vue3 做展示。教学项目要覆盖“业务库→数仓→计算→服务→可视化”的完整链路。

## 2. 10 万到底是什么？

patient_info 的患者人数。原文 generate_data.py 的 TOTAL=100000，每位患者 1 条 patient_info。七表总行数是 2,065,156，单独统计，没有相加冒充 10 万。

## 3. 七张表怎么关联？

patient_info.patient_id 是主键，其余六张表通过 patient_id 外键关联；lifestyle 有 UNIQUE(patient_id)，是一对一；其余是一对多。删除患者被 RESTRICT 阻止。

## 4. 为什么原文没有外键，你要加？

外键用于保证参照完整性，防止孤立记录；这是工程增强，不改变字段业务含义。原文的索引保留了，并补充了日期、疾病、药品、科室等查询索引。

## 5. 数据怎么生成，如何保证不重复？

固定 seed=20261020，按患者 ID 1..100000 生成；疾病 1-3 种、体检 2-4 次、就诊 3-8 次、用药 3-8 条、随访 2-4 次；入库前 --truncate，CSV 覆盖写，不做无控制追加。

## 6. 数据质量怎么检查？

空值、重复主键/患者、孤立外键、非法年龄/血压/血糖/BMI/心率、非法日期、金额勾稽、10 万口径、主外键存在性。结果 7/7 PASS、0 问题。报告在 reports/data_quality_report.json。

## 7. 数据怎么同步到 Hive？

Python 从 MySQL 导出无表头 TSV，NULL 用 \N；本次用 WebHDFS CREATE 实际写入 HDFS，并修正 DataNode 重定向主机名。Hive 建 7 张 ODS 外部表；Spark 从 HDFS 读，写 12 张 HDFS ADS + MySQL ADS。Sqoop 1.4.7 已完成 1000 行 staging；七表全量未执行。

## 8. 这次 HDFS/Hive 跑了吗？

跑了。HDFS NameNode/DataNode 正常，42.31 GB 可用；测试文件 106 bytes，本地与 HDFS SHA-256 一致；7 张 ODS 表 2,065,156 行与 MySQL 完全一致；Hive 3.1.3 建 7 张 ODS 和 12 张 ADS 外部表；Spark 从 HDFS 读 ODS，退出码 0。Sqoop 1000 行 staging 已通过，七表全量未执行。详见 docs/15。

## 9. Spark 具体做了什么？

八个模块：清洗（去重/范围过滤/分级）、画像（group by）、疾病（count distinct/窗口）、风险（多表 join）、就诊（聚合）、用药（row_number top）、趋势（最小二乘）、评分（8 维加权）。结果通过 JDBC 写 MySQL ADS。

## 10. 为什么不用 Hive SQL 直接算？

原文用 Spark SQL；Spark 更适合迭代计算和 JDBC 写出。Hive 已实机建立 ODS/ADS 外部表，Spark 实际从 HDFS ODS 读，结果双写 HDFS ADS 和 MySQL ADS。

## 11. 预测算法是什么？

一元线性回归，y=slope×year+intercept；最小二乘；2018-2025 训练；2026-2029 预测；R²=1-SS_res/SS_tot。实测 slope=3902.6548，intercept=-7868580.7262，R²=0.7361。样本只有 8 个年度点。

## 12. R²=0.7361 算高吗？

不能简单说高或低。它表示历史年度点被直线解释的比例；8 个点、模拟数据、没有外部验证，不能把它当作临床准确率。我们只把它作为拟合优度。

## 13. 健康评分公式？

血压 20%、血糖 20%、BMI 15%、血脂 15%、心率 10%、吸烟 8%、饮酒 7%、运动 5%；每维按分级给 0-100，加权求和保留 1 位；优秀≥85、良好≥70、一般≥55、较差≥40、危险<40；高危<50。

## 14. 缺失值怎么处理？

当前每位患者都有最近体检和一条生活习惯，覆盖率 100%；实现采用 inner join，缺失则不评分。后续可对缺失维度加中立分 60 并标记 imputed，但不能悄悄当成正常。

## 15. 评分能用于诊断吗？

不能。权重来自原文，是规则加权，没有临床验证、没有人群校准；只能用于教学演示和高危提示，不能替代医生。

## 16. 接口怎么设计？

14 个只读接口，统一 code/message/data；分页 page/size；筛选 keyword/gender/level/factor/type/grain；详情 /api/patients/{id}；异常统一处理；CORS 允许 5173/4173；后端只读 ADS，无硬编码。

## 17. 前端怎么保证数据真实？

axios 调 /api，Vite 代理到 8080；每个页面有 v-loading、el-empty、el-alert；截图时后端真实运行；Network 里能看到 /api 请求；没有把数据写死在组件里。

## 18. 怎么证明系统真的跑成功？

MySQL COUNT=100000；质量报告 PASS；Spark 日志退出码 0；ADS 行数；API 14/14；前端 11 张截图；Matplotlib 8 张图；报告和日志都在 reports/logs。数字与文档一致。

## 19. 项目最大的不足？

Sqoop 仅完成 1000 行 staging，七表全量未执行；预测/评分不是临床模型；无权限、无并发压测；前端包偏大；模拟数据不代表真实趋势。回答时主动说，不回避。

## 20. 如果重做，优先做什么？

先把 Sqoop 扩到七表全量，再做权限与增量同步，最后用真实脱敏数据做外部验证；前端做按需加载和移动端适配。

## 21. 为什么后端用 JdbcTemplate 不用 MyBatis？

查询以只读聚合为主，JdbcTemplate 足够直接，SQL 可控，依赖少；MyBatis 更适合复杂动态 SQL/多表映射，本项目不是必须。

## 22. 为什么结果写 MySQL ADS，不直接查 HDFS？

页面需要分页、筛选、详情和稳定响应；每次打开页面启动 Spark 不现实。HDFS 存 ODS 和 12 张 ADS，Hive 提供外部表；MySQL ADS 作为服务层，二者职责不同。

## 23. 代码量/工作量怎么体现？

七表 DDL、Python 生成/入库/质量/同步、PySpark 八模块、14 个 API、11 个页面、15 张 ADS、8 张 Matplotlib 图、16 份文档、18 页 PPT、测试与截图。不是只做一个页面。

## 24. 如何保证可复现？

固定 seed、manifest SHA-256、版本表、环境变量模板、--init/--truncate、脚本化命令、报告与日志；docs/08/09 给出重装步骤。
